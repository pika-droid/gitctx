<context>
Phase 6 Plan 01 provides the core persistent database layer for `gitctx`.
Key architectural pillars:
1. Concurrency: Parallel parsing and template rendering workers stream items over a bounded MPSC channel to a single background writer thread owning the `rusqlite::Connection`, eliminating lock contention and `SQLITE_BUSY` errors under WAL mode (D-01).
2. Atomicity & Crash Safety: Cold indexing writes to `.tmp` files (`.gitctx/index.db.tmp`), executes `PRAGMA wal_checkpoint(TRUNCATE)`, and atomically renames to `.gitctx/index.db` so interrupted or crashed runs leave no corrupted or partial index state (D-02).
3. Schema & Config Validation: Validates `schema_version` and `config_hash` on open, returning actionable fail-fast refusal errors if stale (D-03, INVAR-03).
4. Physical Isolation: Implements `explain_cache` table isolated from all indexing/retrieval queries to enforce Invariant I5 (D-04, INDEX-02).
</context>

<threat_model>
| Threat ID | STRIDE Category | Threat Description | Mitigation Strategy |
| :--- | :--- | :--- | :--- |
| T-06-01 | Tampering | Partial or crashed index write leaves corrupted database state. | Two-phase atomic rename (`index.db.tmp` -> `index.db`) with WAL truncate checkpoint; clean abort removes `.tmp` artifacts (D-02). |
| T-06-02 | Information Disclosure | LLM explanations from `explain_cache` leak into embeddings or search results violating Invariant I5. | Architectural read-gating: indexing and retrieval queries never join or query `explain_cache` (D-04, INDEX-02). |
| T-06-03 | Spoofing | Stale or incompatible index schema opened by newer gitctx version producing undefined behavior. | Validate `schema_version` and `config_hash` on open; fail-fast with explicit rebuild diagnostic (D-03, INVAR-03). |
| T-06-04 | Denial of Service | Lock contention and `SQLITE_BUSY` errors from concurrent indexing worker threads. | Single dedicated background writer thread consuming from a bounded MPSC channel with batch transactions (D-01, INDEX-01). |
| T-06-05 | Elevation of Privilege | SQL injection via malformed function identifiers or commit messages. | All database queries use prepared parameterized statements with typed bindings in `rusqlite` (INDEX-01). |
</threat_model>
