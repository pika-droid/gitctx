II.   LITERATURE REVIEW AND FOUNDATIONS 
The work presented in this paper sits at the intersection of several established research areas: 
mining software repositories, probabilistic information retrieval, hybrid rank fusion, function-
level code identity tracking, statistical co-change coupling analysis, and the emerging problem 
of grounding large language models with structured factual context. Each area is surveyed 
below, with the goal of positioning  gitctx relative to prior art and identifying the specific 
gaps in the literature that it fills. 
2.1  Mining Software Repositories (MSR) 
The Mining Software Repositories (MSR) research community has studied version control 
histories as empirical data sources for over two decades. Foundational work by Hassan and 
Holt [1] demonstrated that historical change data could be used to predict fault-prone modules, 
establishing the central principle that a file's evolutionary past is predictive of its defect-prone 
future. Fischer et al. [2] introduced the systematic study of evolutionary coupling, which is the 
tendency for files that are frequently modified together to encode implicit architectural 
dependencies and showed that such co-change patterns persist and strengthen across successive 
release cycles. 
Moser et al. [3] demonstr ated that change -based metrics derived from version control 
outperform static code metrics for defect prediction, a finding subsequently replicated across 
multiple industrial settings. More recent MSR work has focused on commit message quality 
assessment [4], automated intent classification of commits into categories such as bug fixes, 
feature additions, and refactors [5], and the extraction of issue-closing links from commit trailer 
conventions [6]. Tools such as PyDriller [7] provide programmatic Python APIs for traversing 
Git history, extracting diffs, and computing file -level change metrics, forming part of the 
standard MSR practitioner toolkit. 
gitctx builds upon this established tradition by mining the same foundational sources of 
repository history, including commits, diffs, file trees, and rename events. However, it extends 
beyond conventional file -level statistical aggregation by introducing functi on-level semantic 
indexing, enabling a more granular representation of code evolution and historical 
relationships. Furthermore, gitctx incorporates a natural -language query layer that allows 
developers to retrieve and explore historical insights through i ntuitive questions, a capability 
not typically offered by prior MSR tools.

to ONNX and executed entirely offline through ONNX Runtime, trading maximum retrieval 
quality for the strict offline and deterministic guarantees required by the system's core 
architectural invariants and operational constraints.

2.3  Hybrid Retrieval and Reciprocal Rank Fusion 
Neither lexical BM25 nor dense embedding retrieval dominates the other across all query types. 
Lexical methods excel at exact identifier matching and rare domain -specific tokens; dense 
methods excel at paraphrase and semantic generalization across vocabulary gaps. A substantial 
body of work on rank fusion addresses this complementarity directly. 
Reciprocal Rank Fusion (RRF), proposed by Cormack, Clarke, and Buettcher [13], combines 
ranked result lists from multiple independent retrievers by summing reciprocal rank scores with 
a smoothing constant k:

This formulation produces a fused ranking without requiring score normalization or inter -
retriever calibration. The smooth ing constant k = 60 has been empirically validated across 
TREC benchmarks, demonstrating robustness against outlier high -rank scores. Subsequent 
studies, including the BEIR zero-shot evaluation benchmark [14], have further established that 
RRF consistently matches or outperforms learned fusion methods when training data for a 
supervised combiner is unavailable, making it particularly suitable for newly initialized 
repositories that have not previously been indexed. 
gitctx applies RRF with  k = 60 to fuse BM2 5 and dense retrieval results at query time, 
supplemented by an exact-match fast path that injects function name or commit SHA matches 
at rank 0, guaranteeing their mathematical dominance in the final ranking. 
2.4  Co-Change Coupling and Evolutionary Design Analysis  
The statistical relationship between files that are frequently modified together — termed logical 
coupling or co -change coupling — was formalized by Gall, Hajek, and Jazayeri [11] and 
subsequently system atized in Adam Tornhill's work on evolutionary design analysis [15]. 
The code-maat tool operationalizes these ideas using standard association rule metrics: 
support (how often entities A and B change together), directional confidence P(B | A), and lift, 
which is the ratio of observed joint probability to the expected rate under statistical 
independence. 
=== PAGE 17 (Ch 2) ===
High lift values identify entity pairs that change together far more than chance would predict, 
flagging implicit architectural coupling absent from any sta tic dependency graph. A well -
documented confound in co-change analysis is the presence of mass-formatting or bulk-update 
commits that modify large numbers of files simultaneously, injecting spurious coupling signal 
across otherwise unrelated modules [16].  gitctx addresses this by filtering commits that 
touch more than 25 files and by applying exponential time-decay weighting that down-weights 
historical coupling relative to recent co-change patterns. 
2.5  Function Identity Tracking and Code Lineage 
Tracking the identity of a code entity, such as a function, method, or class, throughout its 
evolutionary history presents a non -trivial challenge. The git log -L command supports 
line-range tracking within a single file but fails to maintain continuity when the containing file 
is renamed or the entity's implementation is moved elsewhere. Grund et al. [17] investigated 
the frequency and characteristics of function moves across large open -source projects, 
demonstrating that cross-file moves account for a significant proportion of refactoring activity 
and expose a systematic limitation in existing code history tracking tools. 
Locality-Sensitive Hashing (LSH) using MinHash , introduced by Broder [18], provides a 
computationally efficient approach for identifying near-duplicate documents without requiring 
exhaustive pairwise comparisons. By generating MinHash signatures from the token multisets 
of function bodies, different versions of a function that retain most of their token content while 
differing in name, signature, or file location can produce similar signatures and high estimated 
Jaccard similarity. gitctx implements a four-tier lineage resolution cascade comprising exact 
key matching, same -file MinHash, Git rename map cross -referencing, and scoped cross -file 
MinHash. This layered approach enables the system to reconstruct complete and deterministic 
chronological chains for individual functions across multiple file renames, code movements, 
and structural refactoring operations. 
2.6  LLM Grounding and the Model Context Protocol (MCP) 
The widespread deployment of large language models as coding assistants has introduced a 
new class of requirements for developer tooling. LLMs possess broad general programming 
knowledge but have no access to a specific project's actual Git history. Their tendency to 
generate plausible but factually incorrect commit attributions and historical rationale has been 
documented in the literature [19]. This hallucination failure mode is particularly harmful for 
=== PAGE 18 (Ch 2) ===
historical why -questions, where a confidently stated but incorrect answer can mislead a 
developer into making a wrong architectural decision. 
The Retrieval -Augmented Generation (RAG) framework [12] addresses this by supplying 
language models with retrieved factual passages at inference time, significantly reducing 
hallucination rates on knowledge -intensive tasks. The Model Context Protocol (MCP) [20], 
introduced as a standardized interface for supplying structured tool outputs to LLMs over a 
stdio JSON-RPC channel, provides a practical deployment mechanism for grounding model 
responses with verifiable, deterministic data from extern al systems without requiring LLM -
side changes. 
gitctx applies the Retrieval -Augmented Generation (RAG) principle specifically to the 
domain of code history. By exposing a set of MCP tools backed by deterministic, offline 
retrieval mechanisms, it enables AI coding assistants to address historical why-questions using 
evidence traceable to specific commit SHAs, authors, and timestamps. This approach reduces 
hallucinations in historical code queries by grounding responses in verifiable repository data, 
while eliminating network dependencies and avoiding LLM inference along the retrieval path. 
As a result, gitctx provides a reproducible and evidence-based foundation for exploring code 
evolution and understanding the rationale behind past development decisions.

III.   SYSTEM DESIGN AND METHODOLOGY 
This chapter details the architectural design and technical implementation of the gitctx 
engine. Building upon the theoretical foundations of software repository mining and 
information retrieval, the proposed system transforms raw version control history into a 
structured semantic knowledge base. The methodology focuses on deterministic offli ne 
processing, resilient function tracking across structural refactoring, and the integration of large 
language models through verifiable retrieval mechanisms. The following sections outline the 
core system invariants, the step -by-step data extraction pipe line, and the hybrid storage 
architecture required to achieve these objectives. 
3.1  Overview and Design Invariants 
The gitctx system is organized as a modular Rust workspace of six crates, each isolating a 
separate architectural concern:  
o gitctx-core: Manages repository Git extraction, abstract syntax tree (AST) parsing, 
the lineage tracking engine, and structured template rendering.  
o gitctx-index: Orchestrates local storage mechanisms, including Tantivy -based 
BM25 indexing and dense vector persistence.  
o gitctx-query: Executes hybrid search retrieval, constructs the statistical co -change 
graph, and performs change impact analysis.  
o gitctx-cli: Exposes the human -facing command -line interface for manual 
developer queries.   
o gitctx-mcp: Operates a Model Context Protocol server to facilitate seamless 
integration with autonomous AI agents.  
o gitctx-eval: Coordinates reproducible benchmarking and generates standardized 
evaluation reports.  
To guarantee deterministic execution, the system arc hitecture is bound by eight mechanically 
enforced invariants, denoted as I1 through I8. The two most critical constraints define the 
operational boundaries of the software:  
1. Invariant I1 (Zero Network Activity):  The system must execute all indexing and 
retrieval operations entirely offline. This constraint is rigorously validated during 
continuous integration (CI) workflows via strict network namespace isolation. 
=== PAGE 20 (Ch 2) ===
2. Invariant I2 (Deterministic Output):  The engine must produce byte -identical 
database states giv en identical repository inputs. This is verified continuously by 
double-indexing a test repository and asserting absolute parity between the resulting 
cryptographic checksums.  
3. Invariant I3 (Incremental Equivalence):  The state produced by incrementally 
indexing one new commit must be identical to the state produced by performing a 
complete full re -index of the repository up to that commit. This prevents the 
incremental code path from silently diverging from the full-index path over time. 
4. Invariant I4 (Non-Null Citations): Every result record returned by a query operation 
must include complete, non -null citation metadata, specifically the commit SHA, 
author name, and timestamp, ensuring that each retrieved result can be traced to its 
corresponding historical source within the repository. Results with missing provenance 
are rejected at the schema layer, ensuring that all retrieved information is fully 
traceable to its source commit. 
5. Invariant I5 (Isolated Explain Cache):  An optional “explain” cache that stores 
additional LLM-generated annotations is maintained in a fully isolated SQLite table 
and is disabled by default. This separation ensures that the deterministic retrieval core 
(I2) cannot be contaminated by non-deterministic LLM outputs introduced through the 
opt-in annotation path. 
6. Invariant I6 (Pinned Evaluation Corpus): The evaluation corpus is pinned at exact 
commit SHAs in a lock file ( eval/corpus.lock.toml) and verified by BLAKE3 
+ SHA -256 cryptographic checksums before any evaluation  run. This prevents 
uncontrolled upstream changes from silently altering the benchmark dataset between 
evaluation runs. 
7. Invariant I7 (Stated Baselines and Uncertainty):  All reported evaluation metrics 
must be accompanied by explicitly stated baseline compa risons and bootstrap 
confidence intervals. Point estimates without uncertainty quantification are rejected by 
the evaluation report generator, enforcing methodological transparency. 
8. Invariant I8 (Explicit First-Parent Traversal): The commit walker must always use 
first-parent traversal mode, never implicit or default traversal. This is enforced in the 
walker configuration and verified by a dedicated test that confirms no second -parent 
commits appear in the indexed dataset for a repository with known merge topology.

These constraints are mechanically validated by a dedicated cargo xtask test -
invariants suite that immediately fails CI builds upon any violation. This rigid enforcement 
ensures the tool remains fully reproducible, auditable, and secure for deploy ment in isolated, 
air-gapped development environments.

The central coordinating structure of repository ingestion is the  IndexPipeline,

Key decisions taken in the indexing pipeline include: 
1. Batched Asynchronous Dual-Write (IndexSink): Instead of performing individual 
disk writes for every function touch, IndexSink buffers up to 128 touch records before 
flushing. It generates embeddings in a single batched ONNX forward pass using 
FastEmbedGenerator::generate_embeddings_batched. Metadata and 
embedding BLOBs are written to SQLite through a non -blocking 
BackgroundWriter, which uses an mpsc queue and a dedicated worker thread. Text 
documents are indexed using Tantivy BM25 within a 32 MB memory budget, while 
normalized 384-dimensional vectors are stored in vectors.bin. 
2. Enriched Schema and Metadata Persistence: The pipeline stores architectural 
metadata for each function touch, including parameter count (arity), change 
classification (change_type), previous signature (signature_before), and the 
128-element MinHash signature as a 512-byte little-endian BLOB (fingerprint). 
The repository's HEAD commit hash (head_at_index) is also recorded in SQLite's 
index_state table. 
3. Dynamic Identifier Delta Extraction:  The pipeline uses 
IdentifierExtractor::extract_from_lines(&rt.diff_hunks) alongside 
D4TemplateRenderer::render_touch to extract added and removed identifiers 
from unified diff lines while filtering standard language keywords. Commit dates are 
formatted as ISO-8601 strings (YYYY-MM-DD). 
4. Chronological Traversal: Commits are collected and reversed to traverse the history 
from the root commit to HEAD. This ensures that function lineage is tracked in 
chronological order, maintaining consistent parent-child relationships across 
successive commits. 
5. Safe Two-Phase Atomic Rotation with Backup Rollback: To handle filesystem 
locking issues, particularly on Windows, AtomicStorageManager uses a staged 
rotation process. Existing index assets (index.db, tantivy, and vectors.bin) 
are first moved to .bak paths before the staged assets are promoted. If promotion 
fails, the previous state is restored from the backups. After successful promotion, 
temporary backup files are removed.

1. Tier 1 (Exact Match): Matches functions with the same qualified name and file path. 
2. Tier 2 (Same -File MinHash):  Identifies modified or renamed functions within the 
same file using MinHash similarity, with a threshold of 0.55. 
3. Tier 3 (Rename Map):  Detects functions relocated between files using rename 
information obtained from Git tree diffs. 
4. Tier 4 (Cross-File MinHash via LSH): Identifies relocated functions across files using 
LSH-based candidate retrieval and MinHash similarity, requiring a score of at least 0.65 
while rejecting potential false matches below 0.20.

4.5  Reciprocal Rank Fusion Implementation 
The query engine fuses lexical and semantic retrieval streams using Reciprocal Rank Fusion 
(RRF) in crates/gitctx-query/src/rrf.rs: 
 
The tie -breaking clause ( then_with(|| a.touch_id.cmp(&b.touch_id)) ) 
mechanically implements Invariant I2 (Topological Determinism). Because  touch_id is 
assigned monotonically in insertion order, ranking outputs are byte -identical across operating 
systems and execution runs. When a query exactly matches a known function qualified name 
or commit hash, the record is injected  at rank zero, mathematically dominating the fused 
ranking.

4.6  Co-Change Analytics and Schema Precomputation 
The coupling engine computes co -change metrics between files and functions. To prioritize 
recent interactions, each event is weighted using an exponential decay function 
(crates/gitctx-query/src/cochange/decay.rs): 
 
Elimination of N+1 Queries via Schema v2 Precomputation  
In earlier prototypes, change impact analysis required over 20,000 individual SQLite queries 
per invocation. To improve performance, the system was redesigned to precompute and store 
co-change metrics during repository indexing. 
1. Schema v2 Analytical Tables: Added  relational tables - cochange_file_metrics 
and cochange_function_metrics, to store precomputed metrics for file and 
function pairs. Composite primary keys and indexes support efficient lookups. 
2. Bulk Computation During Ingestion:  After the process of indexing, 
compute_and_persist_cochange() scans historical file touches in chronological 
order using topo_order. It gro ups changes by commit, excludes bulk commits 
involving more than 25 files and bot-generated commits, and calculates support, time-
decay weighted support (with a half-life of 180 days), directional confidence, and lift. 
3. Faster Impact Queries:  The precomputed metrics are stored in the database and 
retrieved by ImpactService (crates/gitctx-query/src/impact.rs) to 
estimate the potential impact of changes and identify coupled risks. This reduces the 
reported query response time in sub-millisecond durations.
